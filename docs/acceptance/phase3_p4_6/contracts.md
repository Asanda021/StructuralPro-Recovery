# Phase 3 priorities 4–6: supported financial contract

This is synthetic software acceptance, not an official pricebook, signed real contract, authenticated identity, real banking action or native Windows/Office acceptance.

## Statement workflow
The existing `statement_periods`, `build_progress`, `_money`, approved BOQ/pricebook gates and amendment service are retained. Explicit project contract terms select base rates or reviewed sequential estimate factors. Retention, advance recovery, other deductions, tax and insurance are entered explicitly, including zeros. Existing formula: gross minus retention, capped advance recovery and other deductions forms the taxable base; tax is added and insurance subtracted. Rounding is only the documented owner policy. Unknown contractual formulas, row allowances/waste or nonunit row factors are blocked; this implementation does not infer their treatment.

Compatible BOQ sources sharing one price code are projected into a statement row with all original source rows/IDs retained. Incompatible units or rates are blocked. Every BOQ price-code quantity must be explicitly supplied. Identity, contract, date, source, quantities, events and period numbers persist. State transitions are draft, independently reviewed, independently approved and issued. Stale drafts, duplicate references, old revisions and raw writes are blocked. Earlier issued periods are immutable.

Official amendments retain their original before amounts and accumulate signed deltas. Quantity corrections may reduce work through the reviewed amendment route. Optional deduction-rate corrections require all five explicit rates plus owner terms, evidence, reason and independent review/approval/posting. Rates before/after participate in the amendment content seal; old seals without those optional fields remain valid. Current advance capacity applies to the new result, never to recompute the historical before amount. Original issued documents and the global terms are preserved.

## Ledger and cash
Pending document envelopes authorize entries in the existing budget, commitment, cost, payment and receipt collections; they are not a second accounting engine. Commands use owner-documented roles, SHA-256 source evidence, expected project revision and SQLite CAS. Posting and historical revisions are atomic. Every nonempty historical document/bank reference is reserved against reuse. Costs require an approved commitment; payments require the approved cost and its commitment and cannot exceed the remaining invoice. Receipts require an issued statement and cannot exceed its effective net. Negative ordinary records, mixed currencies, missing documents and nonfinite numbers are blocked.

Reversals append evidence and preserve originals. Dependent posted documents must be reversed first. Reducing a statement below an existing receipt is blocked until its receipt is reversed. Actual cash is receipts minus actual payment records (plus explicitly recorded legacy paid-commitment settlement where displayed), never costs plus commitments. Legacy read-only depth, counterparty and aging views project reversals consistently; original stored rows remain untouched. Existing unreviewed legacy entries are not silently promoted into the new verified snapshot.

Budget, cost, payments and receivables remain distinct. Missing dimensions display unknown, not fabricated zero. Budget variance is budget minus accrued cost. Outstanding commitment is commitment minus its linked actual payments; debt is approved cost minus paid invoices. New command records are in one explicit project currency; there is no IRR/IRT conversion.

## Local authority and UI
The owner declaration and source evidence are explicitly entered by the operator. The software attributes actions to locally configured identities; it does not authenticate a human or validate a legal signature. Without documented configuration, financial finalization fails closed. Initial authority configuration is available from the financial workspace, so a new project does not need a Python-only bootstrap. The workspace inherits the existing application theme, RTL and contextual menu/ribbon entry. Jalali input is validated with Qt's calendar and converted to ISO for the existing storage contract. Native Acrylic and Windows behavior are not claimed here.

## Reports and recovery boundaries
Existing PDF/XLSX/DOCX/CSV exporters produce financial and statement reports with Persian labels/units, RTL, Jalali dates, exact amounts, page numbers and editable Word tables. Effective previous/current/cumulative work includes posted amendments. Original and amendment monetary values are distinct. Microsoft Office reopen/save/print and native PowerShell remain external acceptance items.

Backup contains the complete Git ancestry bundle, synthetic SQLite, source fixtures, output reports, logs, JUnit and a SHA-256 Manifest. A source backup is not an EXE or offline dependency installer. Recovered SQLite and reports must be read independently; new end-to-end fixtures run from recovered code. Existing historical absolute source paths are retained as evidence, rather than silently rewriting approval records during relocation.
