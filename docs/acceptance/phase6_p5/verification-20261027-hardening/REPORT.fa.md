## اصلاحات واقعی و RED → GREEN

۱. **W1 / تیر، فاصله تأیید تا ثبت:** در پنج RED، تغییر/حذف PDF، تغییر Revision/عضو یا Cancel در حلقه native QMessageBox امکان ثبت نامعتبر ایجاد می‌کرد. guard پس از Yes دوباره اجرا و Revision پیش از پیام برای CAS ثابت نگه داشته شد. BOQ/takeoffs خالی، digest پس از ورود به پیام ثابت و SQLite پس از Reopen برابرند. Preview تیر طبق قرارداد فعلی می‌تواند Draft ذخیره کند؛ آن را عملیات بدون نوشتن معرفی نمی‌کنیم.

۲. **W1 / بازفعال‌شدن guard قدیمی:** سه RED نشان دادند پیشنهاد تازه با همان زمینه، Wizard تازه یا خاموش/روشن می‌توانست فرم ناتمام لغوشده را دوباره مجاز کند. guard اکنون به Wizard و شیء پیشنهاد آغازکننده مقید است. ورودی ناتمام حفظ می‌شود و بدون handoff معتبر قابل ذخیره نیست. Cancel→Restore پذیرفته‌شده قبلی دوباره پیاده‌سازی نشد.

۳. **E4 / شناسه تکراری:** جست‌وجوی عنوان فقط یکی از دو رکورد هم‌شناسه را می‌یافت و آن را یکتا تلقی می‌کرد. شمارش هویت روی کل snapshot مجاز، قبل از فیلتر عبارت انجام و برخورد در namespace مسیر نیز مسدود شد. رکوردهای هم‌شناسه از نتایج مخفی نمی‌شوند و هیچ مقصدی حدس زده نمی‌شود.

۴. **E4 / طبقه واقعی:** مسیر قبلی فقط focus_member داشت؛ نتیجه طبقه به گره واقعی خود متصل نبود. `focus_project_record` همان درخت Inspector را با هویت یکتای طبقه/عضو انتخاب می‌کند؛ برخورد طبقه/عضو یا پروژه هم‌شناسه رد می‌شود. main در نبود مقصد، خطا می‌دهد و پیام موفقیت جای خطا را نمی‌گیرد. دو RED و آزمون Qt واقعی شاهدند.

۵. **E6 / وابستگی پنهان:** Preview فقط ردیف انتخاب‌شده را نشان می‌داد، درحالی‌که موتور موجود ردیف‌های وابسته را نیز تغییر می‌داد. اکنون بستار متأثر از fingerprintهای همان موتور در پیام تأیید نمایش داده می‌شود. Oracle مستقل A:۶→۳، B:۱۲→۶، C:۱۸→۹؛ مجموع ۳۶→۱۸، Undo→۳۶، Redo→۱۸، Revision جدید، Reopen برابر و BOQ خالی کنترل شدند. این وابستگی ریاضی است؛ آن را مالکیت فیزیکی مشترک معرفی نمی‌کنیم.

۶. **E6 / اتصال CAS پیش‌نمایش به نوشتن:** digest از UI تا `bulk_edit_manual_formulas` و `save_many` منتقل و قبل از اعمال با snapshot معتبر مقایسه می‌شود؛ مرز نهایی SQLite همچنان همان expected_digest تراکنش اصلی است. RED نبود API این اتصال را نشان داد؛ آزمون با اتصال دوم SQLite تغییر پروژه را ایجاد و رد digest کهنه با عدم‌تغییر کل پروژه ثابت کرد. ادعای بازتولید loss یا corruption واقعی در RED API نداریم.

۷. **E6 / مدرک قطعی با مقدار برابر:** تغییر طول/عرض با حاصل‌ضرب ثابت، مقدار وابسته قطعی را ثابت می‌گذاشت ولی مدرک بازبینی را تغییر می‌داد؛ Preview قبلاً آن را می‌پذیرفت و Apply اصلی رد می‌کرد. اکنون fingerprint مدرک وابسته قطعی، حتی در مقدار برابر، Preview را مسدود می‌کند. RED و GREEN مستقل ثبت شدند.

آزمون native پیام گروهی، ردیف وابسته B را در متن واقعی مشاهده و با کلیک No، ثبات digest و صفر BOQ را اثبات کرد. آزمون اولیه این سناریو به دلیل focus/selection نادرست fixture شکست خورد؛ با تعامل واقعی انتخاب جدول پس از تکمیل فیلدها اصلاح شد، نه با ضعیف‌کردن قرارداد محصول.
