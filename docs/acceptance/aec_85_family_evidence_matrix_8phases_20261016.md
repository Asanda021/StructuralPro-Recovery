## قاعده تعبیر وضعیت‌ها
- **شواهد آزمون مصنوعی در دامنه محدود**: مستندات Work و تست‌های تخصصیِ مرتبط در مخزن بررسی شده‌اند. یعنی گردش بخشی از خانواده گزارش و آزموده شده، **نه اینکه همه زیرآیتم‌ها/هندسه‌ها/نقشه واقعی تکمیل باشند**.
- **پذیرش تخصصی مستقلاً احراز نشده**: برای خانواده در این مجموعه شواهد، آزمون اختصاصی کافی نیست. این عبارت به معنی فقدان قطعی کد یا قابلیت نیست؛ رجیستری عمومی/فرم ۸۵تایی دلیل پذیرش نیست.
- **پذیرش نهایی:** صفر خانواده، چون Windows/Office/چاپ/نقشه و دیتایل مرجع واقعی در این بررسی پذیرفته نشده‌اند.
- فازهای **۶ و ۸** دروازه‌های میان‌رشته‌ای‌اند و طبیعی است که خانوادهٔ اصلیِ مختص آن‌ها در جدول صفر باشد. این عدد به معنی صفر بودن فعالیت آن فاز نیست.
- این ماتریس **سند حسابرسی و رهگیری** است، نه اصلاح موتور مهندسی و نه اجرای جدید آزمون جامع؛ `tests_verified` یا `fully_accepted` در بانک مرجع تغییر نکرده‌اند.

## گیت‌های پذیرش مستقل
برای هر خانواده ۹ دروازه ثبت می‌شود: محاسبات تخصصی، رابط دستی، SQLite و تاریخچه، اصلاحیه، اتصال مالی BOQ، خروجی، برداشت تخصصی از نقشه، نمونه واقعی مهندسی و پذیرش Windows/Office. هر گیت تنها به‌صورت `documented_limited` یا `not_verified` باقی می‌ماند. «پذیرفته نهایی» بدون گواه جدید و تغییر عمدی قرارداد اعتبارسنجی ممکن نیست.

## استفاده اجرایی و گام‌های بعدی
۱. هر اصلاح جدیدِ خانواده باید با مرجع محاسبات/فرم/SQLite/BOQ/گزارش و آزمون اختصاصی همراه باشد؛ پس از آن فقط گیت مربوطه با شاهد و دامنه اصلاح شود.
۲. `pytest -q tests/test_aec_evidence_matrix_20261016.py` و آزمون نگهبان ۸۵ خانواده اجرا و نتیجه ثبت شود؛ اجرای تازه روی GitHub Actions قرنطینه‌شده ممنوع است.
۳. ماتریس را برای اولویت‌بندی خانواده‌های فاقد شواهد استفاده کن، نه برای محاسبه درصد تکمیل. گام بعدیِ برنامهٔ چت: واحدهای ساختاریافته متغیرهای سفارشی، سپس یوبوت/کوبیاکس.
۴. نسخه و خروجی نهایی تا آزمون واقعی Windows و تأیید مالک مسدود بماند.

**شفافیت:** فایل‌های این گام صرفاً ماتریس، ابزار اعتبارسنجی و آزمون هستند؛ تست‌های Python در خود این Chat روی مخزن کامل اجرا نشده‌اند (کلون محلی GitHub به دلیل DNS در دسترس نیست). ایجاد تست به معنای PASS آن نیست.
