# فاز ۵ / اولویت ۱ — ایمنی تراکنش SQLite

تاریخ اجرا: ۲۵ اکتبر ۲۰۲۶. مبنای شروع: Commit `c2a103c22eb96dedf0b873dfae51c2ace9a1d3fe` و Tree `8443873c4faaadb3ace9e7da07e6fabb151078ee`.

## نقص اثبات‌شده و RED→GREEN

در شبیه‌سازی واقعی SQLite، `commit()` ابتدا تراکنش را روی دیسک ثبت کرد و سپس خطای «گم‌شدن تأیید COMMIT» داد. نسخه قبلی خطا را به فراخواننده برمی‌گرداند، ولی همان اتصال همچنان قابل استفاده بود و Revision جدید را می‌خواند. آزمون `test_lost_commit_acknowledgement_quarantines_connection` پیش از اصلاح با پیام `DID NOT RAISE RuntimeError` شکست خورد.

اصلاح حداقلی در `ProjectStore` یک latch مستقل برای وضعیت نامطمئن تراکنش اضافه کرد. هر خطا پس از آغاز `COMMIT` یا شکست خود `ROLLBACK` اتصال را قرنطینه و cache را پاک می‌کند. خطای `SQLITE_BUSY` در `BEGIN IMMEDIATE` این latch را فعال نمی‌کند، زیرا هنوز هیچ نوشتنی آغاز نشده و پس از آزادشدن قفل، همان اتصال با موفقیت ذخیره می‌کند.

## آزمون‌های واقعی

- گم‌شدن تأیید COMMIT: خطای save حفظ شد، اتصال قرنطینه شد، اتصال تازه Revision واقعاً ثبت‌شده را برای تطبیق نشان داد؛ هیچ موفقیت کاذب اعلام نشد.
- شکست rollback: اتصال قرنطینه شد؛ اتصال تازه آخرین Revision تأییدشده قبلی را بازیابی کرد.
- `SQLITE_BUSY`: قفل واقعی SQLite در اتصال دوم ایجاد شد؛ ذخیره رد و پس از آزادشدن قفل موفق شد.
- مرگ فرایند با `os._exit(73)` وسط تراکنش واقعی: Revision ناقص منتشر نشد و integrity سالم ماند.
- مجموعه هدفمند DBMOVED، تغییر inode/پوشه والد، startup replacement، CAS، backup snapshot و full-history: **۴۴ PASS، صفر FAIL/ERROR/SKIP** در ۱٫۴۱ ثانیه.

JUnit: `targeted.xml` با SHA-256 برابر `16ab49b25762ea76431ee3350b4b4fb0c4f61373aa9c46f6da20281921f3f33f`؛ لاگ با SHA-256 برابر `8cb7a35b5a840ac2548ef38de821ea82087fcdf1eccb814c7ea53ab64eee8e85`.

## محیط

Linux 6.18.55 x86_64، Python 3.12.14، SQLite 3.53.1، PySide6 6.12.0، pytest 9.1.1 و IfcOpenShell 0.9.0.post1. آزمون واقعی `QApplication` و `QTest.mouseClick` در حالت offscreen موفق شد. این شواهد Windows Native نیست.

## رگرسیون جامع

اجرای مستقیم جامع در collection با ۱۵ ماژول قرارداد تاریخی متوقف شد، چون مبنای زنجیره‌ای PR #25 دارای مسیر فعال `.github/workflows` است و سیاست fail-closed مخزن چنین checkoutی را رد می‌کند. دو خطای collection دیگر نبود IfcOpenShell بودند که پس از آن کتابخانه واقعی نصب شد. فایل‌های `full-collection-blocked.*` این نتیجه را بدون تبدیل به PASS حفظ می‌کنند.

اجرای محصول بدون آن ۱۵ ماژول تا ۴٪ پیش رفت، اما چون P5-2 و P5-3 هنوز کد محصول را تغییر خواهند داد و run حدود دو ساعت برآورد می‌شد، عمداً با exit 130 متوقف شد. `current-suite-interrupted.log` نتیجه آزمون نیست. رگرسیون جامع فقط یک‌بار روی Tree نهایی سه اولویت اجرا می‌شود.

## مرز پذیرش

ایمنی وضعیت نامطمئن COMMIT در Linux با آزمون واقعی تکمیل شد. عامل تاریخی جایگزینی فایل فاز چهار همچنان ناشناخته است و این اصلاح آن را شناسایی یا رفع‌شده اعلام نمی‌کند. رفتار هویت فایل Windows Native و پذیرش مالک مستقل باقی می‌ماند.
